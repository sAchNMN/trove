## A. 先解决"扫描不到 vivo 办公套件里的照片"

### A.1 现在是两条完全不同的扫描路径

| 入口 | 走的技术 | 能看到什么 |
| --- | --- | --- |
| `扫描全部照片 / 视频` | MediaStore 查询（`MediaDiscovery`） | **只**能看到被系统媒体库收录的文件 |
| `扫描设备` | SAF 目录递归（`SortService.scan` → `Storage.children`） | 能看到该目录下真实存在的文件，但要求授权有效 |

截图里状态是 `扫描完成 · 0 个媒体文件 · 0 个已识别 · 0 个非媒体文件未处理`——
这是**第二条路径**的输出（`SortService.java:108`）。三个计数全是 0，说明连"非媒体文件"都没数到，
也就是**该目录一层子项都没读出来**，不是被过滤掉了。

### A.2 四个可能原因（按概率排序）

1. **这个目录从来没进过 MediaStore。**
   `Download` 下的第三方目录（尤其是传输类 App 建的目录）经常带 `.nomedia`，或者文件是 App 自己写进去的、
   没有触发媒体扫描。这类文件 vivo 文件管理自己扫盘能看到，但 `MediaStore.Images` 里根本没有。
   → 所以"扫描全部照片/视频"永远是 0，这是正常的；必须用"补充扫描目录 + 扫描设备"。

2. **文件在 MediaStore 里是 `is_pending=1`。**
   `MediaDiscovery.java:110` 的查询条件是 `is_pending=0 AND is_trashed=0`。
   有些 App 写入媒体时先 insert pending 再 update 成 0，中途被杀就会永久停在 pending。
   文件真实存在、文件管理器能看到，但按这个条件查就是 0。

3. **SAF 授权已经失效，但 App 仍然显示着旧路径。**
   重装、系统"清理"、换机恢复都会让 `takePersistableUriPermission` 的授权消失。
   现在 `sortScan` 只在 `Storage.stat` 失败时才报错；如果 provider 对失效的 tree 返回**空列表而不是抛异常**，
   就会正好得到 0 / 0 / 0，还显示"扫描完成"。

4. **目录其实在 `Android/data/...` 下面。**
   Android 11+ 任何 App 都读不到（`MediaPaths.excluded` 也会直接跳过）。截图路径是 `Download/...`，可以先排除；
   但"vivo 办公套件"如果还有自己的接收目录，要确认一下真实路径。

### A.3 要求 AI 怎么改（这段可以直接贴给它）

1. `SortService.scan()` 开始前，对每个来源目录做一次**预检**并把结果写进状态：
   - 授权是否仍然覆盖该 documentId（`Storage.grants()`）；
   - 根目录 `Storage.stat()` 是否可读；
   - 子项数量（`Storage.children().size()`）。
2. **子项数为 0 时不要显示"扫描完成"**，改成：
   `没有读到文件：该目录可能授权已失效、为空，或被系统限制` + 一个 `重新授权` 按钮。
3. `MediaDiscovery` 增加**兜底查询**：同样条件但去掉 `is_pending=0`，命中的文件标记为"系统尚未发布"，
   在列表里可见但标注原因；不要静默丢弃。
4. 扫描一个目录时**顺带检查 `.nomedia`**：存在就提示"该目录被标记为不参与系统相册，只能通过目录扫描处理"。
5. 每个来源目录行显示真实状态：`已授权 · 128 个文件` / `授权已失效` / `读取失败 · 原因`。
   现在只显示路径，用户完全不知道它到底能不能读。
6. 加一条诊断日志（每个目录：documentId、子项数、非媒体数、异常栈），导出到现有 JSONL 日志里，
   真机排查时不用猜。
7. 如果愿意接受"文件管理类 App"的定位，可以申请 `MANAGE_EXTERNAL_STORAGE` 做**直接文件遍历**兜底，
   MediaStore 只用于写回和回收站。这是唯一能 100% 覆盖 `Download/第三方目录` 的做法。

### A.4 你现在就能做的三步验证

1. 在系统文件管理器里确认 `Download/vivo办公套件` 下有没有 `.nomedia`（有就说明原因 1）。
2. 在 App 里删掉这个来源目录，重新用 `+` 添加一次（会重新走授权），再点`扫描设备`。
   如果这次能读到 → 原因 3。
3. 换一个小一点的子目录（比如 `2021(1)/2021-10`）单独授权试试。

## B. 界面问题逐条对照

对照你给的三张截图。每条都写了"现在的写法 / 为什么错 / 改成什么"，行号是 `MainActivity.java` 里的位置。

### B1. 一屏两个标题（你说的"一个小的一个大的"）

- 现状：`598` 行 `整理 · 本地文件`（11sp 加字距）+ `601` 行 `文件移动分类`（20sp）。
- 为什么错：两行说的是同一件事；11sp 那行还会被误读成"当前所在位置"。
- 改成：**删掉 overline**，只留 20sp 标题。返回/面包屑只在真的有多级页面时出现，放在标题左侧的小返回箭头里。

### B2. 页头一行塞了 4 个东西

- 现状：标题 + `?`（`602`）+ `切换：分步`（`609`）+ 时钟（`616`）。
- 为什么错：`?` 紧贴标题，看起来像标题的一部分；`切换：分步` 是 12sp 的灰底按钮，和主操作抢注意力。
- 改成：标题下方一行 13sp 说明；`?` 移到卡片里；视图切换收进右上角"更多"或放在设置卡里；时钟保留为 48×48 图标。

### B3. 状态行被截断且信息密度过高

- 现状：`619–638`，12sp + 单行 + `ellipsize`，内容是 `● 扫描完成 · 0 个媒体文件 · 0 个已识别 · 0 个非媒体文件…`。
- 为什么错：一句话塞 4 个指标，必然截断；截断后最关键的信息（0 个）反而看不清。
- 改成：状态行只留**一句人话**（`没有读到文件` / `已选择 3 个目录 · 128 个文件`），细节点开看；
  0 结果按 A.3 的第 2 条处理。

### B4. 两个并排按钮，右边那个文字被裁

- 现状：`749–754`，`授权整个 DCIM` / `授权整个 Pictures` 平分宽度，固定 48dp 高。
- 为什么错：你截图这台约 405dp 宽，`授权整个 Pictures` 平分后只剩约 178dp，一定换行，而 48dp 装不下两行 → 裁切。
- 改成：文案缩短为 `DCIM` / `Pictures`（副标题说明"授权整个目录"），或直接竖排两个按钮、高度 `wrap_content`。

### B5. "打开全部照片 / 视频（含 Download）"被裁 + 箭头压字

- 现状：`761–765`，`textButton` 固定 48dp 高，右边还挂了 chevron。
- 为什么错：文案二十来个字 + 固定高度 + 尾部图标 = 换行后第二行被吃掉，箭头落在文字上。
- 改成：改成一个**列表行**（图标 + 主文本 `浏览全部媒体` + 13sp 副文本 + 右箭头），高度 `wrap_content`。
  实现细节（含 Download）从标题里拿掉。

### B6. "分类策略"整块浅灰按钮里只有一个"设备"

- 现状：`884–898`，卡片标题 `分类策略` 12sp，下面整宽 48dp 浅灰按钮，文字居中。
- 为什么错：看起来像输入框/搜索框，不像可点击项；和卡片标题重复；当前值不完整（`设备 / 拍摄年月` 只显示 `设备`）。
- 改成：一行两列 —— 左 `分类策略`（16sp 卡片标题）+ 当前值 `设备 / 拍摄年月`（14sp）+ 右 chevron；整行 56dp 可点。

### B7. 每一张卡都有 `?`

- 现状：`hint()`（`3005–3017`）在标题、目标位置、补充目录、手动扫描、文件夹、分类策略、执行方式、步骤头上各挂一个，
  单页模式一屏能看到 6–8 个灰圆 `?`。
- 为什么错：`?` 是"我不知道这里干嘛"的信号，满地都是等于告诉用户"这个 App 到处都是坑"。
- 改成：一屏最多 2 个，只留给真正非直观的概念（比如"就地分类 vs 目标目录"）。其余改成一行 13sp 灰字，
  或者干脆删掉——靠文案本身说清楚。

### B8. 把需求写在了界面上

- 现状：`2534` 行 `单页模式 · 从上到下完成设置`；`790` 行 `使用"扫描全部照片 / 视频"时不需要再点这里；这里只扫描上面补充授权的目录。`
- 为什么错：这是给开发者的验收标准，不是用户需要的信息。用户只关心"我点这个会发生什么"。
- 改成：删掉第一句；第二句改成按钮文案 `扫描这些目录` + 一行 13sp `只扫描上面添加的文件夹`。

### B9. 字号没有角色，全是"重要"

- 现状：分类页标题 20（`601`）、首页标题 28（`384`）、媒体页标题 28（`514`）、卡片标题 20（`428`、`481`）、
  统计数字 28（`703–705`）、步骤标题 16，正文 12–14 混用。
- 为什么错：三个页面标题分别是 28 / 28 / 20，同一种角色三个尺寸；20sp 又同时是页面标题和卡片标题 → 层级消失；
  28sp 既是页面标题又是统计数字 → 视觉噪音。用户感觉"该小的字很大、不该大的字很大"，根源就是**字号没有绑定角色**。
- 改成：严格按 `docs/UI-SPEC.md` 第 1 章的角色表：页面标题统一 20（`384`、`514` 从 28 改 20）、
  卡片标题 16（`428`、`481` 从 20 改 16）、列表 16 / 正文 14 / 辅助 13 / 元数据 12 / 标签 11；
  28 只留给统计数字（`703–705`），且没有数据时整块不显示。

### B10. 底部导航太重，还压住内容

- 现状：`3094` 行 tab 88×60，选中态是整块纯黑药丸（`3116–3129`）；内容区底部 padding 128（`672`），导航浮层 92（`688`）。
- 为什么错：纯黑 88×60 的块在浅色页面上是视觉中心，比主按钮还重；滚动到底时最后一张卡被盖住一半。
- 改成：导航高 64，选中态改为浅灰底 + 图标/文字变黑；内容底部 padding = 导航高 + 24 + 系统手势区。
- **显隐改为只跟手指**：向下滚收起，停手不自动出现，向上滚或回到顶部才出现（详见 `docs/UI-SPEC.md` 第 7 章）。

### B11. 空状态没有出口

- 现状：`暂无扫描结果` 只是一个空卡片。
- 改成：`还没有扫描结果` + 一行原因 + 一个 `扫描全部照片 / 视频` 按钮。

### B12. 数字卡片 28sp 三个数字抢戏

- 现状：`699–713`，照片/视频/待确认三个 28sp 数字。
- 改成：数字 20sp、标签 12sp；或者在没有数据时整块不显示（现在 0/0/0 也占一整张卡）。

## D. 第 4 轮：0.7.0 真机复检（vivo V2419A / 347dp 宽 / fontScale 1.0）

这些是规范写进仓库、前 3 轮改完之后，在真机上仍然能看到的问题。截图见 `captures/v071-*.png`。

### D1. 分步模式的底部操作条是浮层，正好盖住「扫描这些目录」

- 现状：`footerLayer` 是 `body`（FrameLayout）里的一层，`Gravity.BOTTOM` + 90dp 底部 padding，浮在 ScrollView 上。
- 现象：默认滚动位置下，来源列表和「扫描这些目录」被它盖住一半；用户必须先滚动才知道下面还有入口。
- 改成：把操作条移出 FrameLayout，作为 `shell` 纵向布局的最后一块；`sortPage` 的底部 padding 从 `NAV_HEIGHT + 148` 收回 `PAGE_BOTTOM`。
- 验收：操作条顶部不再压住任何控件；内容在它上方滚动；导航条可见时两层不重叠。

### D2. 「下一步：分类预览」被 50dp 固定高度的按钮裁掉

- 现状：`Wizard.nextLabel` 返回 9 个字，按钮 `new LinearLayout.LayoutParams(0, dp(50), 1)`，半宽约 155dp。
- 现象：文字折成两行，第二行被 50dp 高度切掉一半（截图里只剩上半截字）。
- 改成：按钮文案改成 `下一步`（下一步做什么由步骤标题承担），高度 `wrap_content` + `setMinHeight(dp(50))`。
- 顺带：`WizardTest` 同步断言新文案，避免以后又改回去。

### D3. 首页流程行「03 确认执行」在 347dp 上折行

- 现状：三个 `stepChip` + 两个箭头，各带 padding，总宽超过 315dp。
- 改成：一行 12sp 文本 `01 选目录 → 02 勾选分类 → 03 确认执行`，删掉 `stepChip` / `flowArrow`。

### D4. 标题下的状态行只显示一行就被切断

- 现状：状态行是「6dp 圆点 + TextView(weight 1, maxLines 2)」，实测在 347dp 上只排了一行，42 个字直接溢出被父容器裁掉，连省略号都没有。
- 改成：去掉圆点 View，文本用 `● ` 前缀、整行宽度；同时把状态文案里「复用缓存 / 索引范围」删掉，只留「待整理 / 已归档跳过 / 用时」。
- 验收：状态 2 行显示完整；点状态仍可看全文。

### D5. 「已整理过的文件被当成 0 个文件」

- 根因：`MediaPaths.excluded()` 把 `分类` 当成排除目录，导致已经整理过的文件在扫描时全部消失，状态显示「扫描完成 · 0 个媒体文件」。
- 改成：
  - `MediaPaths` 拆成 `hidden()`（`Android/data`、`Android/obb`、点目录、`cache`、`thumbnails`）和 `archived()`（任一层叫 `分类`），`excluded()` 仍是两者并集，私有目录继续永远不读；
  - `MediaDiscovery.listDetailed(context, includeArchived)` 统计 `skippedArchived`，`MediaLibrary.Result` 透传；
  - 整理页扫描卡新增开关「包含已归档的文件」（默认关），文案「重新整理「分类」里已整理过的文件」；
  - 开关关：状态写「待整理 2033 · 已归档跳过 2772」；开关开：4805 个候选；
  - 重新整理时用 `MediaPaths.archiveBase()` 截断到第一个 `分类` 之前，避免 `分类/分类`；目标目录与来源同一层时直接跳过。
- 实测：关 2033 / 0.4 秒（缓存复用）；开 4805 / 130.1 秒 / 新增 2772；两种状态下 `find -type d -path '*分类/分类*'` 均为空，MediaStore 仍是 4021 张图 + 784 个视频。
